# 风险与对策

| # | 风险 | 信号 | 对策 |
|---|---|---|---|
| R1 | **服务陷阱**：收入随人头线性，"顶着软件估值的咨询公司" | 模板复用率不涨、每单成本不降、harvest 产出为零 | WS-G 制度先行（Phase 0 就开 harvest review）；收割 owner 是编制内角色不是自觉；度量月度公开 |
| R2 | **雪花部署**：每单独特、无抽象沉淀 | 交付分支/私有 fork 出现；同类集成第二次仍全手工 | 红线：bespoke 逻辑只进客户 scope 数据不进平台代码；admission 工具化（WS-D3）压发现成本；ontology 模板化（WS-A）让"建模客户业务"本身可复用 |
| R3 | **NyxID 随附部署复杂度**（Tier2）：四合一依赖的私有化远重于 aevatar 本体 | Tier2 手册在干净环境拉不起来；slug 重注册出错率高 | Tier1 优先消化多数客户；Tier2 只对明确大单启动，先做一次内部完整演练再承诺客户；与 NyxID 侧仅通过部署配置协作（不改代码） |
| R4 | **数据驻留需求超前**：合规客户直接要求 per-tenant 隔离 | 销售被 Tier3 缺失卡单 | Tier3 触发条件与成本模型先写清（03-roadmap 不做清单）；用 Tier1 hybrid（数据不出客户环境、只有编排在托管侧）承接大部分合规诉求 |
| R5 | **带宽冲突**：本路线与 aevatar 生产稳定性 milestone 抢同一批人 | P1/P2 里程碑连续滑期 | 路线显式让位于生产稳定性；Phase 0 全部是零代码项，不占平台工程带宽 |
| R6 | **channel 未绑定降权的兼容成本**：绑定机制已存在（ADR-0018），但把未绑定发送者从"owner 环境配置"改为 restricted catalog 会改变存量群体验 | 收尾上线后存量群功能回退、投诉上升 | 渐进切换：对存量 scope 提供过渡窗口与公告；降权目录保留基础问答能力，只收敛凭证类工具 |
| R7 | **评测集冷启动**：新客户域没有历史 turn 可 replay | eval gate 变成空转或被跳过 | bootcamp day5 的验收基线就是首个 eval 集（人工构造 10–30 条）；replay 评测随运行量自然增厚；禁止用"跳过 eval"换交付速度（对齐 FI-006） |
| R8 | **AI FDE 过度承诺**：agent 交付员在客户面前失败损伤信任 | 客户自助操作产生高失败率工单 | 演进三段论不跳级：先副驾驶后自助；关键步骤保留人审批；失败路径必须给 typed 补救而非沉默 |
| R9 | **本方案自身的雪花化**：blueprint 与 aevatar 仓库脱节 | 方案引用的机制在主仓库演进后失效 | 方案落地项一律转为 aevatar 仓库 issue/milestone 管理；本 repo 只保留策略层，不复制实现细节 |

## 明确的不确定性（诚实清单）

- 外部数字（FDE 岗位增长、试点失败率、竞品估值）多为单一来源或媒体口径——方向可信、精度存疑，本方案的论证不依赖其精确值。
- WS-A 的对象实例物化规模（高基数客户数据）未做容量评估；MVP 限定"运营对象"量级（10²–10⁴ 实例/scope），大数据量场景显式留在外部系统、只建模引用。
- Tier2 的 NyxID 随附部署可行性基于"部署≠修改"假设，未与 NyxID 侧实际演练——P3-M2 内部演练是第一个检验点。
- 评测语料捕获（P2-M1）需要新的脱敏/保留 ADR；在它通过评审前，eval 相关里程碑的范围可能收缩。
